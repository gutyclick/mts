# Checkout measurement

Apply the additive migration `20261103000200_checkout_funnel.sql` with the normal reviewed migration process before releasing the application changes. This work does not apply migrations to production, take payments or create eSIMs.

`recordCheckoutStats(kind)` in `src/lib/analytics/client.ts` accepts only these stage names: `checkout_entry`, `contact_ready`, `payment_ready`, `coupon_attempted`, `coupon_applied`, `coupon_rejected`, `payment_attempt`, and `payment_error`. Call entry and readiness measurement again on `mts:stats-permission` when the corresponding state is already satisfied, because consent hydration is asynchronous. Repeated calls are safe: the database's `(cohort_hash, kind)` primary key counts each stage once per session. Coupon and payment metrics count sessions experiencing an outcome, not total attempts.

The client checks affirmative statistics permission, DNT/GPC and the exact localized checkout path. The existing same-origin public event route validates a strict event union, bounds request size, checks signed consent, privacy headers and bot exclusion, and uses the existing rate-limited short-lived session. No customer input, email, coupon code, order identifier, Stripe error message, payment detail or arbitrary metadata is accepted in checkout events. Paid cannot be submitted by browsers: existing live-order attachment and paid-status trigger remain authoritative. Event failures remain optional and never block checkout.

The admin API requires admin membership and MFA and calls service-only aggregate RPCs. Checkout cohorts are consenting sessions with a recorded `checkout_entry` whose first checkout entry falls in the selected period. Counts for each stage are independent observations within those entry cohorts; they do not assert sequential progression and may overlap. A session can correct a rejected coupon and appear in both rejected and applied counts. A restored payment can skip readiness observations. The existing destination funnel remains independently counted, including historical sessions collected before this migration.

An unpaid checkout whose first entry was less than 30 minutes ago is **incomplete/still open**. A checkout cohort is **matured** once 30 minutes have elapsed from its first recorded `checkout_entry`, regardless of earlier browsing time; **matured unpaid** is the measured abandonment numerator, with all matured entry cohorts as denominator. This is session-window abandonment, not a claim that the traveler never purchased: later payments are outside existing attribution. Paid entry cohorts require existing server-authoritative live paid events and an authoritative order payment timestamp at or after first checkout entry, within 30 minutes of that entry. A prior purchase in the same consenting session does not convert a later checkout, including when asynchronous order attachment emits its paid event late. The existing original session still limits event collection and paid attribution: browsing for 25 minutes before checkout leaves only five minutes of collection, but the report waits a full 30 minutes after checkout entry before treating the cohort as matured. It does not extend the session or claim that all those 30 minutes were observed. Financial totals continue to include all live paid orders, including customers who decline statistics, and do not form the funnel denominator.

Matured unpaid cohorts are partitioned into four mutually exclusive observed stop groups: `afterAttempt` when a payment attempt was observed; otherwise `beforeContact` when contact readiness was not observed; otherwise `formUnavailable` when payment readiness was not observed; otherwise `beforeAttempt`. These counts sum to matured unpaid, even for restored checkout paths that skip readiness events. They describe the last observed state, not proven reasons for abandonment.

Measurement begins on deployment; blockers, declined consent and technical failures can reduce observations. Checkout telemetry has the same 30-day retention and withdrawal behavior as existing cohorts: the foreign key cascades on cohort deletion, and no new persistent identifier or storage is introduced. Public/authenticated database roles cannot read stages or execute their recorder/admin RPCs.

Run focused verification with:

```sh
node --experimental-strip-types --test tests/checkout-analytics.test.mjs tests/analytics.test.mjs tests/analytics-security.test.mjs tests/analytics-withdrawal.test.mjs
```

The tests execute the original analytics and additive checkout migrations in local PGlite, check deduplication, maturity, server-only paid confirmation, revocation, retention, admin authorization and database privileges. Browser tests mock transport to verify consent, DNT/GPC and path restrictions; they never contact Stripe or the eSIM provider.
