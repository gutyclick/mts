# SimCoins Implementation Plan

> **For agentic workers:** Use subagent-driven-development for independent tasks; retain shared financial contracts below and review every integration against the existing checkout invariants.

**Goal:** Integrate a bilingual, auditable rewards program into the existing application, prepared for launch but transactionally disabled.

**Architecture:** Pure integer financial engine; service-only PostgreSQL transactions and append-only postings; immutable per-order/per-unit commercial snapshots; narrow adapters around existing checkout, verified payment, fulfillment/delivery and refund paths. Existing customer and MFA-protected admin shells remain authoritative. No deployment or remote migration execution is authorized for this feature yet.

**Tech Stack:** Existing Next.js 16.4.3 App Router, React 19, TypeScript, Supabase/PostgreSQL, Stripe, eSIM Access, Resend and PGlite tests.

**Spec:** Owner's full SimCoins implementation request in this conversation; this document records implementation decisions and progress without superseding that request.

## Global constraints

- `SIMCOINS_ENABLED=false` by default. Separate public, earning, redemption and admin flags. No live enablement, remote migration, deployment, charge, emission or refund during implementation.
- One coin is one USD cent; 100 coins = USD 1. Whole coins, earned by rounding down. No transfer, cash withdrawal or ordinary expiry.
- Existing accounts/authentication, order money snapshots, provider fulfillment and refund ownership remain intact. No historical backfill, catalog price changes or supplier cost writes.
- Owner ruling: initial Viajero / Traveler is a separate 0% tier; the first qualifying purchase unlocks Explorer for subsequent purchases. Four earning tiers: 3/4/5/6% at first eligible purchase / USD 60 / USD 125 / USD 300.
- USD gross `amount_total` / `unit_amount` remain canonical catalog snapshots. SimCoins commercial snapshots store net eligible USD cash, redemption and reward liabilities. Frozen payment amounts remain actual selected-currency per-unit amounts; never use an unverified browser discount or relax Stripe identity checks.
- Stripe budget 440 bps + USD 0.30; foreign currency 540 bps + USD 0.30; minimum contribution 2000 bps of actual cash collected. Affiliate reference 800 bps, maximum general promotion 500 bps. Redemption is subtracted once from revenue, never again as an expense; earned coin liability is a separate cost.
- Initial release delay proposal: seven days after verified delivery, configurable; no change to statutory/refund rights. Actual delivery means validated provision plus signed `email.delivered`, not email API acceptance. A zero delay is supported in local tests.
- Successful refunds restore original redeemed coins proportionally as promotional credit and reverse original earned coins/tier spend using original unit allocations, not current FX. A spent reward reversal can create auditable debt that blocks further spending until covered.

## Review focus

- Two simultaneous checkouts must not spend the same available postings.
- Unknown Stripe creation/payment outcomes retain reservations; browser leave alone never releases them.
- Quantity and zero-decimal currency rounding must agree with existing per-unit payment checks.
- Duplicate/out-of-order payment, delivery and refund events must have unique business postings and preserve money snapshots.
- Disabled flags and missing configuration/cost/provider/delivery evidence fail closed without breaking ordinary checkout.

## Ledger and concurrency contract

Append-only signed postings in pending/available/reserved buckets, independently idempotent by source key. Reservation transfers available → reserved; paid settlement consumes reserved; authoritative terminal unpaid state compensates reserved → available. Release moves pending → available with compensating postings. Eligible spend has its own signed field and is never inferred from wallet balance. Account row locking serializes reserve/refund/settlement/release. No mutable balance is the source of truth.

Snapshots are created only for newly participating orders. Financial state changes use trusted existing order/refund/fulfillment records. All browser mutations derive the actor from auth; critical admin actions require existing MFA assurance, membership, a reason, a request ID and audit logs. Customer responses omit wholesale costs, Stripe/private installation identifiers and internal audit metadata.
